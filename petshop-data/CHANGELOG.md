## v1.1 · 2026-09-15 · 一致性修订

### 1. 退款口径：全场景退入余额（P0）

**问题**：文档同时存在「微信付退微信、余额付退余额（1–3 个工作日）」「手动原路退回」两套说法，而代码里**没有任何一条退款链路是通的**（无退款端点、`refund_apply` 是孤岛表、无微信支付基建）。

**结论**：退款一律退入会员**可用余额**，即时到账；不提供退微信 / 退现金出口，余额亦不支持提现；赠送金一并退回、不折现。

| 文档 | 位置 | 变更 |
|---|---|---|
| PRD | 3.4 业务逻辑、3.5 原型页 + 业务逻辑 + 标注、4.3 订单管理、4.5 会员详情、4.6 退款规则、4.9 会员详情、5-4 / 6-2 Mermaid、7 NFR | 旧口径 → 一律退入可用余额 |
| 技术设计 | 3-6 支付与退款 | 删除「调微信退款 API」，改为余额入账三步事务；微信退款列为二期 |
| 技术设计 | pay_order.status | 注明 `REFUNDED` 当前不使用，二期需补 REFUNDING / REFUND_FAILED |
| 规划 | 3-1 MVP 功能清单 | 退款审核行改为余额口径 |
| UI 稿 | 「我的」页 | 补「退款记录」入口（一期实际能力） |

**同时修掉的真实缺陷**：
- 技术设计 4.1 的 `可退本金 = 余额 × (cum_principal ÷ (cum_principal + cum_gift))` **在多笔充值场景下必然算错**——`cum_*` 是历史累计（只增不减），余额是当前值，两次充值赠送比例不同即失真。充 1000 送 150 → 消费 575 → 再充 100 送 0 时公式给 **594.00**，真实剩余本金 **600.00**（顾客少退 6 元）；第二次若为「充 100 送 100」则公式给 **631.48**（商家多退 31.48 元），差额方向会翻转。**改为 `可退本金 = Σ balance_ledger.principal_amt`**（消费/退款流水记负值直接相减），并补「分位误差一律计入赠送金」的归属规则。
- PRD 3.5 原型页演示数值 `¥396.75 / ¥59.45` 是「先凑总数再倒推」，与公式不符（正确 396.70 / 59.50）。该页已整体重做为「次卡退款 + 退款记录」，不再展示比例折算。

## v1.2 · 2026-09-15 · 商品订单链路 + 后台管理端 + 退款提醒

> 触发：需求方提出「用户点申请退款 → 后台有提示 → 管理员确认后才退款」。
> 排查后发现**申请、待审态、审核、退入余额这四段代码都在，唯独缺「后台界面」和「提示机制」**，
> 于是店长根本无从得知有人申请退款 —— 整条链路在最后一步断掉，且退款来源只有次卡一种。

### 1. 退款来源：次卡 → 次卡 + 商品订单（新增 GOODS）

`RefundSource` 由单一金额改为 `(amount, principal, gift)` 三元组，审核通过时按来源分派：
`CARD → CardService.markRefunded`、`GOODS → MallOrderService.markRefunded`（置 `PAID → REFUNDED` 并**回补库存**，与入余额同事务）。

**关键取舍：退款按「原支付构成」而非「当前余额构成」拆分本金/赠送金。**
订单在下单时就落了 `principal_paid` / `gift_paid` 两个快照字段，退款按该比例还原。
若改用「当前余额里本金与赠送金的比例」，用户退款前后又充过值就会算错，且错的方向不可预测（可能多退也可能少退）。

### 2. 商品订单链路：mall 模块从空壳建成

改动前 mall 模块只有实体、没有一行业务代码（无下单、无订单、无购物车、无数据），
所以「退款扩展到商品订单」实际等于**先把整条订单链路建出来**。

| 环节 | 实现要点 |
|---|---|
| 下单 | 只接受 `skuId + qty`，金额服务端按 SKU 现价算；**下单即锁库存** |
| 库存 | `UPDATE sku SET stock = stock - qty WHERE id = ? AND stock >= qty` —— 用 CAS 而不是「先查后改」，并发下不会超卖 |
| 核销码 | 8 位数字 + 唯一索引，撞索引重试 5 次；核销走 `PAID → VERIFIED` 条件更新，天然一次性 |
| 支付 | 一期仅余额支付；赠送金优先扣，扣减比例由服务端算并落快照 |
| 取消 | `CREATED → CANCELLED` + 库存即时回补 |
| 退款 | `PAID → REFUNDED` 作为**最终防线**：CAS 返回 0 则整个退款事务（含库存回补）回滚，同一单不可能退两次 |

**已核销的订单不给退**（`GoodsOrder.isRefundable` 只认 `PAID`）。

### 3. 后台管理端（自建，零构建）

形态定为**纯静态 HTML/CSS/JS，由 Spring Boot 直接托管在 `/manage/`**：无需前端工具链、无需单独部署、和接口同源没有跨域问题。

- **响应式三档**：手机（底部标签栏）/ 平板（抽屉侧栏 + 汉堡按钮）/ 桌面（常驻侧边栏），断点 1024px。
- **三套主题**：标准 / 喵喵 / 汪汪，色值与小程序**完全同源**（#B8551D / #E8638C / #2E7CD6），主题选择存 localStorage。
- **覆盖范围**：待审看板、退款审核（含人工退款）、订单管理、预约管理、核销台（服务码 + 商品码分两个入口）、到店结算、通知自检。
- 鉴权沿用既有 `AdminTokenInterceptor`（`X-Admin-Token`），未新增账号体系。

### 4. 退款提醒：后台角标 + 微信订阅消息

需求方要「两种都要」，落地为**角标为主、推送为辅**：

| 通道 | 实现 | 失败时 |
|---|---|---|
| 后台角标 | `GET /admin/refunds/pending-count`，前端 30s 轮询 + 顶部铃铛 + 标签栏角标 | 不影响任何资金动作 |
| 微信订阅消息 | `wx_subscribe_quota`（店长 openid → 剩余次数）+ `notify_log` 留痕 | **静默降级为仅角标**，绝不让推送失败影响已提交的退款事务 |

推送用 `@TransactionalEventListener(AFTER_COMMIT)` 触发：只在退款申请**真正落库后**才发，
且 `WxSubscribeService.notifyRefundApplied` 全程 try/catch 不抛异常 —— 通知是锦上添花，不能反过来把主流程拖垮。

**顺带回答了「仍未处理 #9」的一半**：微信一次性订阅消息「一次授权只能发一条」的约束，
现在由配额表显式建模（发送前 `remain >= 1` 才算得动，失败自动退还配额），
不再是靠假设绕过去。剩余未定的是**续订引导**（何时、以什么文案引导用户再次授权）。

### 5. 修掉两个实现层缺陷（都会被误判为「后端数据被删了」）

| # | 缺陷 | 症状 | 根因 |
|---|---|---|---|
| 1 | **MyBatis-Plus 分页插件从未注册** | `size=5` 返回 7 条、`total` 恒为 0 | 全项目没有 `PaginationInnerInterceptor`。缺它时 MP **不报错**：count 不执行、`LIMIT` 不拼，service 里那些「size 上限 100」的收敛全部空转 |
| 2 | **雪花 id 在 JSON 里以数字下发** | 后台点「通过并退款」提示「退款单不存在」 | id 是 19 位，超出 JS `Number` 安全整数范围（16 位），前端一 `JSON.parse` 就被静默截断成另一个数 |

第 2 条影响面比表面大：会员端「撤回退款申请」、小程序确认预约、结算、删除宠物、
编辑宠物档案**全部**因为 `Number(dataset.id)` 而打错目标 —— 这类缺陷在数据量小、id 位数短时完全看不出来。

**修法**：Jackson 层把 `Long` 统一序列化成字符串（`ToStringSerializer`），
前端一律把主键当字符串处理（新增 `SnowflakeId` 类型别名，禁止 `Number()`）；
代价是计数器（`total` / `pendingCount`）也变成字符串，展示无影响、做算术需显式转换 —— 已写进测试固化，避免后人当漏配改回去。

两个缺陷都补了回归测试：`PaginationRegressionTest`（断言 `records.size()` 恰等于 `size` 且 `total > 0`，
只断言「返回了数据」是发现不了的）与 `SnowflakeIdContractTest`（断言出参是带引号的字符串且原样往返）。
