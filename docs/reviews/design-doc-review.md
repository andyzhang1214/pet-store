## 一、P0：事实性错误与文档间正面冲突

### P0-1 余额退款公式在多笔充值场景下会算错（技术设计 4.1 + 代码同源）

技术设计 4.1 与术语表定义：

```
可退本金 = 当前余额 × (cum_principal ÷ (cum_principal + cum_gift))
```

`cum_principal / cum_gift` 是**历史累计**值（代码 `MemberAccountMapper.recharge` 只增不减，消费不回冲），而乘数是**当前余额**。两次充值若赠送比例不同，两者不再可比，公式必然失真。按代码逻辑复算：

| 场景 | 真实剩余本金 | 公式结果 | 差额 |
|------|------|------|------|
| 充 1000 送 150 → 消费 575 → 再充 100 送 0 | 600.00 | **594.00** | 顾客少退 6.00 |
| 充 1000 送 150 → 消费 575 → 再充 100 送 100（促销） | 600.00 | **631.48** | 商家多退 31.48 |

差额不大但方向会翻转，属于必然发生的客诉与对账差异来源。"自定义充值不享赠送"这个功能本身就会稳定制造第一种场景。

**PRD 自己的示例也算错了**：3.5 原型页写"余额 ¥456.20 / 累计本金 ¥1,000 / 累计赠送 ¥150 → 可退本金 ¥396.75"，正确值是 `456.20 × 1000/1150 = 396.70`；赠送分摊文档写 ¥59.45，正确值 `59.50`。两个数加起来确实是 456.20，说明是**先凑总数再倒推**，而非按公式计算。

**建议**：改为维护"剩余本金"余额（流水 `principal_amt` 累加即为剩余本金，零新增字段且对账恒等式更强），公式退化为 `可退本金 = Σ流水 principal_amt`。同时在 PRD 术语表明确**分位误差归属**（`HALF_UP` 到分后差额归商家还是顾客），这是必须写死的规则。

### P0-2 时段到底落不落库：PRD 与技术设计说法相反

- **PRD 3.3**："时段**不落库**，由有效预约的起止时间实时聚合计算，保证改配置即时生效。"
- **技术设计 3-3 / 4.3**：有 `time_slot` 表，`UNIQUE(store_id, slot_date, start_time)`，预约事务内 `SELECT ... FOR UPDATE` 锁定时段行、维护 `booked_count`，"时段行生成（**懒创建**）时固化该值"。

这是两份文档在**核心并发方案上的正面冲突**，不是措辞差异。实现目前走的是技术设计路线（`TimeSlotMapper` 有 `booked_count` 与 `lockByNaturalKey`）。PRD 那句"保证改配置即时生效"与技术设计的"懒创建时固化、仅对后续新时段生效"是相反的产品承诺。

**建议**：以技术设计为准，回改 PRD 3.3，并明确回答一个被绕开的问题——**已生成时段的 `capacity` 固化后，店长改容量对已存在的未来时段是否生效**。这是店长一定会问的第一个问题，目前两处答案相反。

### P0-3 模块数自相矛盾：14 vs 15，8 vs 9

- `plan.md`："C 端 **6** 个功能模块 → B 端 **8** 个功能模块"（6+8=14）
- PRD 开篇："共 **14** 个功能模块"
- PRD 正文：3.1–3.6 = **6** 个，4.1–4.9 = **9** 个 → 实为 **15** 个

根因是 `plan.md` 的"B 端 8 个"过期未同步，PRD 开篇继承了 14 而正文已扩到 9。同类问题在 PRD 4.8 与 `plan.md` 对健康档案的描述上也已出现（PRD 增加了"体重趋势"这一记录类型，`plan.md` 未反映）。

### P0-4 同一门服务在 PRD 内部存在两套互不相容的价格宇宙

这是全部冲突里对开发伤害最大的一条。第 3 章（顾客端）与第 4 章（后台）的价格、服务名、次卡售价**完全对不上，且各自内部自洽**：

| 维度 | 第 3 章（顾客端原型） | 第 4 章（后台原型） |
|------|------|------|
| 服务命名 | 猫咪洗澡 / 猫咪精致洗护 / 猫咪美容修剪 / 狗狗洗澡 / 造型修剪 | 洗护套餐 / 精致美容 / 药浴 SPA / 寄养（日） |
| 猫的毛长档位 | 短毛 / 长毛（**两档**） | 猫·短毛 / 猫·中长毛 / 猫·长毛（**三档**） |
| 长毛猫洗护单价 | ¥128 | ¥180 |
| 短毛猫洗护单价 | ¥88 | ¥120 |
| 长毛猫洗澡 10 次卡售价 | ¥1,080（3.5 原型，单次 ¥128 自洽） | ¥1,440（4.6 表格，¥180×10×8折 自洽） |
| 短毛猫洗澡 10 次卡售价 | ¥760（单次 ¥88 自洽） | ¥1,080（¥120×10×9折 自洽） |

注意第 4 章不是"错"——4.1 预约列表"冻结 ¥158"、4.2 收银台"¥180 × 88 折 = ¥158.40"、4.5 价格矩阵"猫·长毛 ¥180"三者严丝合缝。第 3 章的 ¥128 体系同样自洽。**问题是两套体系之间没有任何映射表**，而且 3.1 的宠物档案表单让用户三选毛长（短毛/中长/长毛），3.2 价目表却只给猫两档——**中长毛猫按第 3 章根本无价可查**。

PRD 是"可直接作为设计与开发输入"的定位，价格是唯一不能有歧义的东西。这也直接解释了我此前代码审查中发现的 `DEWORM`/`WORM`、`cardName`/`name` 一类契约断裂：**缺乏单一事实来源，各端各自解释文档**。

### P0-7 UI 设计稿含二期功能，且首页/价目表结构与 PRD 冲突

同一段还有两处结构漂移：

UI 稿看起来是更晚的设计决策（时间戳 09-15 02:41，晚于 PRD 的 02:48 之前那批），但 PRD 未回写。**这三处是"设计稿领先于 PRD"还是"设计稿跑偏"，需要你拍板**；无论哪种，三者必须收敛到一个答案。

## 二、关键设计缺口（该有而没有）

以下不是错误，是缺失。缺的这几块恰好都是**上线后会立刻被问到的**。

| # | 缺口 | 为什么必须补 |
|---|------|------|
| G-1 | **埋点与数据看板设计** | 规划 1.2 定义了 5 个可核查目标（线上预约占比 ≥60%、储值复购 ≥2 次/月、商品购买率 ≥15%），但 PRD 3 章只有"浏览"没有"上报"，技术设计无埋点表，后台"经营概览"PRD 明说"不单独展开"。**这 5 个目标当前无法被度量**，月度复盘将无据可依 |
| G-2 | **枚举 / 字典对照表** | 全文档唯一定义的枚举是 `appointment.status` 与 `card.status`。而 `verify_code` 冲突、`DEWORM` vs `WORM`、`SOON` vs `DUE_SOON`、次卡/订单/退款状态机横跨四份文档各自表述——这正是本次代码审查中契约断裂的根因。建议单开一份《枚举字典》作为唯一事实来源 |
| G-3 | **`refund_apply` 字段定义与跨渠道退款状态机** | 表 3-6 只有一行"退款申请"，无字段。而退款要同时覆盖：微信原路退（1–3 工作日）、余额即时退（含本金/赠送分摊）、次卡退、部分退款。`pay_order.status` 只有 `CREATED/SUCCESS/CLOSED/REFUNDED`，**无法表达"微信退款处理中"**。这是资金链路上唯一没有完整状态机的地方 |
| G-4 | **关单后回调成功的处置** | 4.6 与流程 5.3 规定"15 分钟未支付自动关单并释放库存"。但微信回调可能在第 16 分钟成功到达——此时库存已释放、订单已关闭。文档未定义该分支（应转退款还是重新占用库存）。这是支付类系统的经典故障，且必然发生 |
| G-5 | **一次性订阅消息的额度限制** | 4.7 要求"到期前 7 天与 3 天各发一次"，但微信**一次性订阅消息一次授权只能发一条**，"长期订阅"仅对特定行业类目开放（宠物生活服务类目不具备）。不解决则"7 天 + 3 天双发"在技术设计上不成立。同类问题也影响 PRD 4.9 列出的 5 类通知开关 |
| G-6 | **时区与 `CURDATE()` 风险** | 技术设计 2.1 写"时间一律数据库本地时区统一存储"，但 4.2 预扣用 `valid_until >= CURDATE()`、4.7 用 `DATE_ADD(CURDATE(), INTERVAL 1 YEAR)`。云托管 MySQL 默认时区若为 UTC，核销与到期判断会整体偏移 8 小时（晚间 16:00–24:00 的预约将判定异常）。应显式声明连接串时区，并**禁止 SQL 内使用 `CURDATE()/NOW()`**，统一由应用层传入 |
| G-7 | **次卡抵扣的金额口径** | PRD 4.2 说"改用次卡抵扣时该行不再叠加会员折扣，并释放原冻结余额"，但没定义**次卡 1 次抵扣多少金额**——原价？折后价？该行整额？同时 `DiscountEngine.calc(items, memberLevel, activities, manualPrice)` 的签名里既没有"次卡抵扣"也没有"担保抵扣"两个维度，说明引擎抽象未覆盖 PRD 4.2 定义的完整结算链路 |
| G-8 | **错误码表 / 幂等矩阵 / 定时任务清单 / 索引清单** | 技术设计仅在 4.1 出现过 `BIZ_BALANCE_NOT_ENOUGH` 一个错误码；幂等键散落 5 处（`pay_no`、核销 CAS、`uk(pet_id, log_id, notice_day)`、库存、对账）；定时任务散落 3 处（5 分钟查单补偿、每日对账、每日到期扫描）；无一处索引清单。这四张表是**上线后必查的四张表**，应收敛成独立章节 |
| G-9 | **可用性、容灾与变更回滚** | 1.2 明确 Caffeine 本地缓存"应用必须单实例部署"，但 8.1 同时写"蓝绿发布，支持灰度"。**蓝绿期间新旧两实例并存，验证码与限流计数必然不一致**——这两条互相否定。且单实例意味着无横向扩容能力，未给 RTO/RPO 目标，也未给数据库变更的回滚脚本流程（我已产出的 `03_migration.sql` 就需要这个流程） |
| G-10 | **验收条件（AC）** | PRD 各模块给的是散文式"业务逻辑"，没有可测的 Given-When-Then。我在修复阶段写回归测试时，判定标准全部由代码反推而非文档给出。**文档无法直接驱动测试**，是 PRD 与实现漂移的结构性原因 |
| G-11 | **MVP 范围未回答"寄养是否含在一期"** | 规划 3.1 MVP 清单含"服务分类（洗护 / 美容 / **寄养**）"；PRD 3.3 写"MVP 如未开通寄养则该分类隐藏"；PRD 4.5 服务表里"寄养（日）"为**停用**状态。而寄养按天计费、跨夜占用、容量以"位"计，与按次服务是**两套完全不同的担保与结算模型**，全文只有一句话带过。请明确剔除或补设计 |
| G-12 | **商品订单部分退款** | 3.4/4.3 支持"多商品合并结算"，但退款只有整单维度。一单三件退一件是否可行、库存如何回滚、`total_paid` 如何冲减，均未定义 |

## 三、结构性优化建议（写作与维护方式）

这一节是"为什么会有上面这一堆问题"的答案。

**S-1 建立单一事实来源（SSOT），给每个数字指定唯一归属地**

现状是四份文档各自内嵌演示数值，谁都可以改，改了不同步。建议按"规则 / 数值 / 实现"三分：

| 内容类型 | 唯一归属 | 其他文档的做法 |
|------|------|------|
| 业务规则、字段规则、状态机 | PRD | 技术设计只引用条目编号，不复述 |
| 价格、档位、折扣、示例数值 | **一份独立数据集**（JSON/表格） | 三份文档全部从中取值渲染 |
| 表结构、SQL、并发方案 | 技术设计 | PRD 不复述实现 |

我这次的修复已经吃过这个亏：`03_migration.sql` 与 `01_schema.sql` 必须手工保持一致，本质上和文档是同一个问题。

**S-2 让文档里的示例数值可被机器校验**

P0-1（396.75 vs 396.70）、P0-4（¥128 vs ¥180）、P0-5（送 ¥30 vs 送 ¥45）全部是**改一个数忘了改另一个**。把演示数据抽成数据文件后，加一条 CI 脚本断言"文档展示价 = 数据集价 = 种子数据价"，这类问题从此不会漏网。这是投入产出比最高的一条建议。

**S-3 决策记录加编号，文档正文可反查**

规划第 4 章有 21 项决策（很好的实践），但没有编号（D-1…D-21），PRD 与技术设计只能写"见规划第 4 章"而无法精确指向某一条。建议给决策编号，并允许正文以 `[D-07]` 形式引用——**当某个数值有争议时，追溯链能直接落到那一条决策上**。

**S-4 术语表补"实现命名"列**

术语表只有业务术语，没有对应的字段名/枚举值。`DEWORM`（前端）vs `WORM`（后端）这类断裂，就是缺这一列的必然结果。建议术语表扩为三列：业务术语 / 实现命名 / 定义。

**S-5 补一份轻量 ChangeLog**

四份文档都写"版本 v1.0"，但文件时间戳显示 09-14 至 09-15 之间连续修改过多次（UI 稿与 PRD 时间不同步即由此产生）。没有变更记录，就无法判断"以哪份为准"。哪怕只记录"日期 / 文档 / 变更点 / 影响范围"也足够。

**S-6 UI 稿应标注"一期 / 二期"**

带优惠券的「我的」页是一期视觉，优惠券是二期功能。建议 UI 稿对每个画出来的元素标注范围，避免设计与开发各自理解一圈范围。

## 五、值得保留的部分
